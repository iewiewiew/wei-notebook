# 分析 Pull Request 差异输出测试用例

## 使用示例

```text
1. 完整后端单仓：帮我分析后端PR差异，源分支lx/feat-premium-dot-numeric-username、目标分支premium/release-v260630-normal，参考已有测试用例模板，生成用例输出到/Users/menghuawei/workspace/my-project/gitee-work/02.需求测试/PR测试用例集合/目录
2. 精简前端单仓：解析前端phc/feat/numeric-dot-user-path对比release/v260630-normal-premium的diff，输出md格式测试用例
3. 前后端联动：同步分析后端源分支lx/feat-premium-dot-numeric-username、目标分支premium/release-v260630-normal，前端源分支phc/feat/numeric-dot-user-path、目标分支release/v260630-normal-premium两处PR差异，联动梳理前后端交互改动点，同时生成csv/md/xmind三套测试用例，标注接口联调风险点
4. 附加增强：分析diff后标注高风险改动，额外补充旧功能回归测试点
```

## 一、环境与仓库基础配置

### 1.1 后端服务仓库

- 本地仓库路径：`/Users/menghuawei/workspace/work-project/gitee`
- 切换分支命令：`git checkout 分支名`
- 标准对比 diff 命令：

```shell
cd /Users/menghuawei/workspace/work-project/gitee
git fetch origin
git diff origin/【源分支】 origin/【目标分支】
```

- 示例分支对照
  - 源分支：`origin/feat/premium-admin-audit-log`
  - 目标分支：`origin/premium/release-v260430-geely`

### 1.2 前端 Web 仓库

- 本地仓库路径：`/Users/menghuawei/workspace/work-project/gitee-ent-web`
- 标准对比 diff 命令：

```shell
cd /Users/menghuawei/workspace/work-project/gitee-ent-web
git fetch origin
git diff origin/【源分支】 origin/【目标分支】
```

- 示例分支对照
  - 源分支：`origin/phc/feat/user-login-history`
  - 目标分支：`origin/release/v260430-normal-premium`

### 1.3 测试用例输出存储路径

默认输出目录：`/Users/menghuawei/workspace/my-project/gitee-work/02.需求测试/PR测试用例集合/`

**文件命名规则**（三种格式共用同一主文件名）：

```text
PR用例-{端}-{源分支短名}-yyyyMMdd.{csv|md|xmind}
```

- `{端}`：`后端` / `前端` / `联动`
- `{源分支短名}`：取源分支名，将 `/` 替换为 `-`；联动场景取**后端源分支**短名（两端功能关键词一致时可改用功能关键词）
- 同分支同日重复分析时：追加时分 `-HHmm`，如 `PR用例-后端-feat-premium-admin-audit-log-20260723-1430.csv`

示例：

| 场景 | 文件名 |
|------|--------|
| 后端单仓 | `PR用例-后端-feat-premium-admin-audit-log-20260723.csv` |
| 前端单仓 | `PR用例-前端-phc-feat-user-login-history-20260723.md` |
| 前后端联动 | `PR用例-联动-feat-add-department-watchdog-config-20260723.xmind` |

分支名过长时，可用功能关键词替代源分支短名：`PR用例-{端}-{功能关键词}-yyyyMMdd.csv`（如 `PR用例-后端-audit-log-20260723.csv`）。

## 二、适用使用场景

1. 新功能开发、线上 BUG 修复完成，提交 PR 等待主干合并阶段；
2. 版本合并准入评审环节，快速评估改动测试覆盖率、输出测试准入依据；
3. 快速迭代、小批量频繁发布场景，替代人工逐行读代码写用例，提升测试产出效率；
4. 各类代码变更类型全覆盖：逻辑重构、接口入参/出参调整、判断分支 if/else 改动、循环逻辑修改、新增三方依赖、删除废弃方法、数据库 SQL 变更、权限校验逻辑改动；
5. 质量管控要求严格环境，杜绝无测试覆盖、漏测改动点直接合并发布；
6. 多人协作并行开发，多分支合并前批量校验各 PR 改动测试完整性；
7. 前后端同步迭代、接口联调修改场景，统一梳理两端联动改动测试范围。

## 三、核心执行指令 & 执行步骤

### Step1：信息接收与解析

1. 识别用户输入标识：区分**后端 / 前端 / 前后端联动**仓库；
2. 提取必填参数：源分支名、目标分支名；可选附加参数：输出格式（csv / md / xmind / 多格式）、是否开启高风险标记、是否追加回归用例、是否引用历史参考用例、输出目录；
3. 拉取完整 git diff 数据：变更文件清单、新增行(+)、删除行(-)、修改上下文代码、导入包/依赖、注释改动、SQL 语句、接口定义、前端组件/接口请求逻辑；
4. 前后端联动场景额外动作：匹配前端请求接口与后端接口实现代码，梳理参数传递、返回体映射差异。

### Step2：改动类型分类标记

逐文件逐代码块归类，每个改动点绑定唯一编号；前后端联动场景分前缀标记 B-后端、F-前端、BF-联调交互点：

- 【新增】全新类/方法/接口/页面组件/按钮交互
- 【逻辑修改】原有方法内部执行流程、判断条件、运算规则变更
- 【删除】废弃函数、冗余分支、无用前端页面、旧接口
- 【参数变动】入参增减、参数类型修改、默认值调整、出参字段变更
- 【分支条件】if/else、switch、三元判断、阈值边界修改
- 【依赖变更】新增第三方包、升级依赖版本、移除依赖库
- 【数据存储】SQL 增删改查、字段长度/索引、数据库事务逻辑改动
- 【权限/校验】登录鉴权、角色权限、参数校验、格式正则调整

### Step3：业务逻辑拆解分析

对每一条标记改动点深度拆解；前后端联动场景打通整条请求链路：前端页面操作 → 接口请求参数 → 后端接收校验 → 业务处理 → 数据库存储 → 返回数据 → 前端渲染展示

1. 所属业务模块、调用链路（谁调用、被谁依赖）；
2. 输入约束：必填项、数据类型、取值范围、格式规则；
3. 内部执行逻辑：分支走向、计算规则、异常抛出点；
4. 输出结果：正常返回值、错误码、页面渲染效果、数据库写入内容；
5. 关联上下游：是否影响其他接口、前端页面、定时任务、回调逻辑。

### Step4：多维度场景用例覆盖设计

每个改动点必须配套多维度场景，无遗漏；BF 联调点额外增加跨端交互校验用例：

1. ✅ 正向正常场景：符合标准入参、流程完整走通
2. ❌ 反向异常场景：非法参数、空值、错误格式、越权操作
3. 📏 边界值场景：临界数字长度、最大/最小阈值、空集合、超长文本
4. ⚠️ 容错降级场景：超时、数据库失败、依赖服务不可用时程序表现
5. 🔄 关联回归场景：改动影响的旧功能、历史稳定流程
6. 🔗 联调专属场景：前端传参格式与后端校验规则匹配、后端返回字段前端正常渲染、异常错误码前端弹窗提示正常

### Step5：标准化用例结构输出

生成前**必读** `references/` 下示例，严格对齐字段、层级与文风：

- [测试用例导入样例.csv](references/测试用例导入样例.csv)
- [测试用例示例.md](references/测试用例示例.md)
- [测试用例示例.xmind](references/测试用例示例.xmind)（可解压查看内部 `content.json`）

#### CSV（结构化导入测试平台）

表头固定（勿增删列、勿改列名），UTF-8 编码，对齐 [测试用例导入样例.csv](references/测试用例导入样例.csv)：

```text
序号,功能模块*,用例名称*,维护人,用例类型,优先级,前置条件,备注,步骤描述,预期结果
```

- 功能模块*：用 `/` 划分目录层级，最多五级（如 `分支管理/分支创建规范/命名规范校验`）
- 用例名称*：一句话可判定的验证点
- 用例类型：功能测试 / 性能测试 / 接口测试 / 安全相关 / 兼容性测试 / UI测试 / 其他（默认功能测试）
- 优先级：P0 / P1 / P2 / P3 / P4（默认 P0）
- 步骤描述 / 预期结果：多步骤用换行分割，顺序一一对应

#### Markdown 标准排版

对齐 [测试用例示例.md](references/测试用例示例.md)：

1. 首行用引用块写 PR 元信息：`> PR信息：后端源分支… 后端目标分支… / 前端源分支… 前端目标分支… | 生成时间：yyyy-MM-dd`
2. 模块（`## **模块名**`）→ 子模块（`- 子模块名`）→ 验证点（缩进 `- 验证…`）
3. 每个验证点一句话、可执行、可判定，避免「功能正常」类空话

```markdown
> PR信息：后端源分支xxx 后端目标分支xxx / 前端源分支xxx 前端目标分支xxx | 生成时间：yyyy-MM-dd

## **模块名**
- 子模块名
  - 验证正向场景…
  - 验证边界/异常场景…
## **非功能需求**
- 兼容性 / 性能 / 安全性 / 易用性
  - 验证…
```

#### XMind 脑图

结构与 MD 大纲同构：根节点标题建议为 `{功能/主题}-测试用例`（或与主文件名一致的 `PR用例-{端}-{源分支短名}-yyyyMMdd`）→ 一级模块 → 子模块 → 验证点（叶子节点，文案与 MD 一致）。根节点 notes 可写入 PR 元信息（与 MD 首行引用块一致）。

格式为 XMind Zen（ZIP 包，含 `content.json` / `metadata.json` / `manifest.json`），用 Python `zipfile` 写入，节点树对应 `rootTopic.children.attached`。生成后确认可用 XMind 打开。对齐 [测试用例示例.xmind](references/测试用例示例.xmind)。

**多格式一致性**：MD 验证点、CSV 用例、XMind 叶子节点须可互相追溯（CSV 可对同一验证点细化多条，但不可遗漏），模块/子模块命名三者保持一致。

### Step6：风险标记与质量提示

1. **高风险判定标准**：支付/权限/审核日志、SQL 变更、核心登录逻辑、接口鉴权、数据删除逻辑、批量操作、前后端接口字段大规模调整；
2. 中风险：普通业务查询、页面展示、非核心字段修改；
3. 低风险：注释调整、日志打印、样式 UI 微调、常量文案修改；
4. 针对高风险点强制追加多条异常、并发、脏数据、跨端联调测试场景。

### Step7：输出约束规则

1. 用例与 diff 改动点一一绑定，不生成和本次 PR 无关的冗余旧用例；
2. 所有代码变更行 100% 有测试覆盖，无漏改漏测；前后端联动场景保证整条请求链路全覆盖；
3. 可按需单输出 CSV / MD / XMind，或同时生成多份文件（同主文件名、不同扩展名）；
4. 文件名严格遵循 `PR用例-{端}-{源分支短名}-yyyyMMdd`，分支名中的 `/` 必须替换为 `-`；同日同分支重复分析追加 `-HHmm`，避免覆盖；
5. 若用户提供参考用例样本，统一对齐样本的书写风格、粒度、术语规范；
6. 前后端分开梳理改动清单，再合并生成联调综合用例，区分单端自测与两端联测步骤。

## 四、约束与边界限制

1. 仅分析当前源 vs 目标分支差异，不对比历史其他发布分支；
2. 无法自动执行自动化测试、跑接口，只产出人工/自动化可执行的用例文本；
3. UI 视觉样式微调类改动仅标注页面校验点，不细化像素级视觉步骤；
4. 若 diff 存在二进制文件、图片、静态资源，单独备注资源替换校验项；
5. 支持批量多个 PR 依次分析，按各自源分支短名与端别分开生成独立命名的用例文件；
6. 前后端仓库代码独立解析，不会混淆两端文件路径与代码逻辑。
